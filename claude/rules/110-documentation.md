# Documentation

Documentation should describe actual behavior, not aspirations.

## Public interfaces

Document meaningful:
- purpose and behavior;
- parameters and return values;
- errors or failure modes;
- important constraints;
- representative examples when useful.

## Internal code

Document non-obvious behavior, constraints, and reasons.

Do not write documentation that simply paraphrases the implementation.

## Accuracy

Update documentation when behavior changes.

Do not invent API behavior, configuration, commands, or examples.

When documentation and implementation conflict, verify which one reflects the intended current behavior before
changing either.

## Examples

Prefer small, runnable or directly applicable examples.

Do not include examples that depend on unstated setup.
