# API design

Use these rules when designing or changing APIs.

Preserve existing contracts unless the task requires a breaking change.

Use established HTTP, RPC, or project-specific conventions consistently.

Validate inputs at the boundary.

Use meaningful status/error semantics appropriate to the project's existing API style.

Keep error responses stable and actionable.

Consider authentication, authorization, idempotency, pagination, filtering, sorting, rate limits, and
backwards compatibility when relevant.

Do not introduce new response shapes when an existing project convention already covers the case.

Document externally visible behavioral changes.
