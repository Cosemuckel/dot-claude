# Naming and comments

Names should communicate intent.

Prefer names that describe the domain concept, action, state, or invariant being represented.

Avoid vague names such as `data`, `thing`, `helper`, `manager`, `process`, or `result` when a more precise
name is available.

Comments should explain why, constraints, or non-obvious behavior.

Do not comment obvious syntax or restate the function name.

When changing behavior, remove or update comments that no longer describe reality.
